# ربط الذمم بالعملاء كتكاليف مباشرة — 2026-10-25

## الاستخدام

- عند إضافة ذمة، اختر العميل من «العميل — تكلفة مباشرة اختيارية». ترك الاختيار عامًا يعني تكلفة على الشركة.
- للذمة الموجودة قبل أول دفعة، اضغط «ربط بعميل» أو «تعديل الربط»، ثم اختر العميل واكتب سبب التغيير. يمكن نقل الربط أو إزالته.
- تظهر التكلفة في «العملاء ← صافي العملاء»: المصروفات المدفوعة المرتبطة بالعميل + باقي الذمم المرتبطة غير المدفوعة.
- مثال: ذمة تصوير 500$ تعني تكلفة مباشرة 500$ قبل الدفع. دفع 150$ يجعلها مصروفًا مدفوعًا 150$ + ذمة متبقية 350$، فيظل إجمالي التكلفة 500$؛ وبعد الدفع الكامل يبقى مصروف 500$ فقط.
- ربط الذمة لا يعني سدادها، ولا يغيّر المبالغ المستحقة على العميل أو قيمة عقده، ولا ينشئ حركة صندوق أو قيدًا عكسيًا.

## حماية الدفعات السابقة

تغيير `Liability.clientId` بعد وجود دفعات قد يجعل قيود الدفع المحفوظة مرتبطة بعميل مختلف عن الذمة، ويخالف اتساق تطبيقات الدفع في قاعدة البيانات. لذلك يمنع الأمر تغيير الربط إذا وجدت **أي دفعة سابقة، ولو عُكست لاحقًا**. يظهر الزر معطّلًا وسبب واضح. الذمم الجديدة والذمم غير المدفوعة التي لا تملك تاريخ دفعات قابلة للربط. لا تعاد كتابة القيود القديمة أو إنشاء قيود مالية لنقل تكلفتها. إعادة تصنيف الذمم ذات تاريخ الدفع تحتاج مسارًا منفصلًا متفقًا عليه؛ ليست ضمن هذا التعديل.

## التنفيذ

- `liability.setClient`: معرف الذمة، العميل المطلوب أو `null`، العميل السابق المتوقع، وسبب التعديل. يرفض المبالغ أو اسم محرر مرسلًا من المتصفح.
- `setLiabilityClient` في `lib/finance/service.ts`: تحقق المنظمة والذمة والعميل وعدم وجود دفعات، ثم تحديث الربط فقط. يستخدم معاملة Serializable وحماية الطلبات المكررة القائمة. التحقق المشروط يمنع الكتابة فوق ربط قديم أو دفع متزامن.
- يحفظ `AuditEvent` القيم السابقة والجديدة مع `source: liability-client-link`، ويسجّل حساب المالك من الخادم وتوقيت قاعدة البيانات. `buildLiabilityClientHistories` يبقي كل تعديلات الذمة، مع عرض التوقيت بدمشق.
- `clientDirectCosts` يستخدم قيم USD من snapshot النشط، ويجمع بوحدات عشرية ثابتة الدقة (أربعة منازل). يضيف فقط المتبقي من الذمم، ولا يضيف إجمالي الذمة مرة ثانية إلى دفعاتها. الحساب تراكمي للبيانات المعروضة، وليس توزيعًا شهريًا جديدًا للتكاليف.
- قيد دفع الذمة الجديد يرث ربط العميل الموجود أصلًا من `payLiability`، لذلك ينتقل المدفوع تلقائيًا إلى مصروفات العميل.

لا migrations أو تغييرات صلاحيات أو تعديلات نشر. لا تعديل تلقائي للذمم القائمة؛ التغيير يحصل فقط عند حفظ المستخدم اختيارًا من الواجهة. مشكلة القيد العكسي عند تعديل ملاحظات حركة نقدية موضوع مستقل ولم تُعدّل هنا.

## التحقق

- نجحت 98 حالة اختبار، وفحص TypeScript وESLint وبناء الإنتاج، داخل نسخة مؤقتة من نفس ملفات المشروع وملف القفل. تعذّر تشغيل أدوات النسخة الأصلية بشكل موثوق لأن أجزاء من `node_modules` كانت ملفات سحابية غير محمّلة؛ لم تعدّل حزم المشروع أو ملف قفله لمعالجة ذلك.
- اختبارات `tests/liability-client.test.ts` تغطي الربط والنقل والإزالة، منع تعديل ذمم لها دفعات، العميل/الذمة غير المتاحين، ربط قديم أو دفع متزامن، القيم الصارمة، سجل التعديلات، والتكلفة قبل وبعد الدفع الجزئي والكامل.
- نجح اختبار API فعلي باستخدام Next.js وPrisma وقاعدة PGlite مؤقتة (PostgreSQL عبر WASM)، مع migration المشروع الكامل وقيوده. تحقق من عدم إنشاء أي قيد صندوق عند الربط، حفظ سجل التعديلات بعد إعادة القراءة، idempotency، رفض ربط قديم، توريث العميل إلى دفعات الذمة، بقاء التكلفة 500$ قبل الدفع وبعد دفع 150$ وبعد السداد الكامل، وقفل الربط بعد الدفع. جميع السجلات كانت وهمية ولم يتصل الاختبار بقاعدة المستخدم.
- تمت معاينة نموذج الربط وسجله وقفل الذمة المسددة وعمود إجمالي التكلفة في المتصفح؛ ظهر العميل A بتكلفة مدفوعة 500$، والعميل B بذمة غير مدفوعة 75$، دون تكرار.
- يبقى اختبار PostgreSQL التشغيلي على staging قبل النشر مطلوبًا، خصوصًا تزامن طلب الدفع مع تعديل الربط وصلاحيات حساب التطبيق؛ قاعدة WASM ذات الاتصال الواحد لا تثبت سلامة التزامن متعدد الاتصالات.
