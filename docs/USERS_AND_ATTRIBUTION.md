# المستخدمون وصلاحياتهم واسم مُدخل السجل — 2026-11-01

## الاستخدام

- تبويب «المستخدمون» يظهر لحساب المالك ولأي حساب بصلاحية «تعديل».
- «إضافة مستخدم»: اسم ظاهر بالعربي، اسم دخول إنكليزي، كلمة مرور، وصلاحية. استخدم اسم الشخص الحقيقي في حقل «الاسم الظاهر في الحركات».
- «مشاهدة فقط»: عرض جميع الأقسام المالية، بما فيها الرواتب، والبحث والتقارير والتصدير. لا إضافة أو تعديل أو دفع أو عكس أو أرشفة أو تغيير سعر صرف، ولا إدارة مستخدمين. هذه ليست صلاحيات على مستوى أقسام منفصلة.
- «تعديل — مدير»: نفس صلاحيات المدير، بما فيها جميع العمليات المالية وإضافة المستخدمين وتعديل صلاحياتهم وتعطيلهم. هذا مقصود حسب طلب المالك؛ لا تمنحها لمن يحتاج إلى المشاهدة فقط.
- «تعديل / تعطيل»: تعديل الاسم والصلاحية، تفعيل/تعطيل، أو وضع كلمة مرور جديدة. حقل كلمة المرور الفارغ يبقيها كما هي. اسم الدخول ثابت حفاظًا على ربط سجلات التدقيق.
- التعطيل لا يحذف المستخدم أو أي حركة سابقة. التغيير يسري على طلبه التالي، ولا يلزم الانتظار لانتهاء جلسة مخزنة.
- حساب المالك الموجود في `ADMIN_USERNAME` و`ADMIN_PASSWORD` يبقى كما هو، ومحمي من التعطيل أو التعديل عبر الجدول. لا ينشئ التطبيق مالكًا جديدًا ولا يسمح بإسناد `OWNER` عبر API.

## الدخول وكلمات المرور

الدخول يستخدم نافذة HTTP Basic الحالية للنظام، لا صفحة دخول جديدة. يُدخل كل شخص اسم حسابه وكلمة مروره. لتجربة حساب آخر دون تغيير الحساب الحالي، استخدم نافذة خاصة أو متصفحًا آخر؛ المتصفح قد يحتفظ ببيانات Basic حتى إغلاقه. لا تُحفظ كلمات المرور في localStorage ولا تُعرض بعد الحفظ.

حسابات الأشخاص في جدول `AppUser`، مرتبطة بالمؤسسة. كلمات المرور بصمات `scrypt-v1` مع salt عشوائي مستقل (`N=32768, r=8, p=1`)، وليست نصًا واضحًا أو تشفيرًا قابلًا لفكّه. الحد الأدنى 12 محرفًا وبينها 6 محارف مختلفة، والحد الأقصى 128. يبقى شرط كلمة مرور المالك الإنتاجية الحالي دون تخفيف.

يوجد تقييد محدود للعملية لمحاولات الدخول الفاشلة: خمس محاولات للحساب خلال دقيقة، مع تحديد التحقق المتزامن. هذا ليس بديلًا عن rate limiting على مستوى الخادم/البروكسي عند النشر؛ ولا أُضيف أي تغيير لإعدادات النشر بهذا التعديل.

## حماية الخادم

- `authenticate()` يتحقق من حساب المالك الحالي أو من بصمة مستخدم فعّال في القاعدة، ولا يقبل هوية أو صلاحية من جسم الطلب أو رؤوس يرسلها العميل.
- `/api/finance` يتحقق من الصلاحية قبل قراءة أو تنفيذ أي أمر مالي. حساب المشاهدة يحصل على `403` حتى لو أظهر الأزرار يدويًا أو أرسل POST مباشرة.
- `/api/users` مقفول للمدير/المعدّل. `/api/auth/me` يرجع الهوية العامة فقط، دون بيانات حساسة.
- تبقى حماية الأصل HTTPS وJSON وحد الجسم وZod والتحقق المالي وidempotency الحالية فعالة. API يعيد التحقق مستقلًا عن Proxy؛ لا يُفترض أن تجاوز Proxy يسمح بأي وصول.
- Proxy لا يتصل بقاعدة البيانات: يسمح لقالب الصفحة الثابت الخالي من البيانات باستقبال Basic header سليم البنية لمستخدم إضافي، ثم تتحقق `/api/auth/me` وجميع واجهات البيانات من كلمة المرور الفعلية والصلاحية. كلمة مرور خاطئة قد تُحمّل قالب الانتظار فقط، ولا تسمح بقراءة أي بيانات مالية. عند إضافة صفحات SSR أو Server Actions مستقبلًا يجب وضع التحقق داخلها أيضًا، لا الاعتماد على Proxy.
- صلاحية الحساب والتعطيل وكلمة المرور تُقرأ من القاعدة لكل طلب جديد، دون cache جلسة طويلة. في الإنتاج، غياب إعداد المالك الآمن يفشل مغلقًا كما سابقًا. يبقى وضع التطوير المحلي دون إعداد حساب بنفس سلوكه السابق، لكن بيانات دخول صريحة خاطئة لا تتحول إلى مالك محلي.
- تعديل مستخدم يعتمد على `version` لمنع الكتابة فوق تعديل أحدث. إنشاء/تعديل المستخدم وسجل تدقيقه ضمن transaction؛ لا حذف نهائي ولا إعادة استخدام اسم حساب موجود.
- واجهة المستخدم لا تعرض أزرار التغيير للمشاهد، لكن هذا ليس حد الحماية الأساسي؛ الخادم يمنعها أيضًا.

## «تم الإدخال بواسطة …»

يظهر الاسم بخط صغير تحت السجل/الحركة في الدخل، المصروفات (العامة والمرتبطة بعميل)، الصندوق، العملاء، الاشتراكات، الذمم، الموظفين وتسويات الرواتب، السلف، الثوابت والخدمات، وحسابات المستخدمين.

- هوية المحرّر تأتي من المصادقة على الخادم عبر `AsyncLocalStorage`، لا من اسم مكتوب في النموذج.
- يبقى اسم الدخول في `AuditEvent.actor` كمعرّف مراجعة، ويؤخذ snapshot للاسم الظاهر في `metadata.actorName` وفي `CashEntry.createdBy` للحركات الجديدة.
- تعديل الحركة لا يغيّر اسم مُدخلها الأول: الحركة البديلة تحتفظ باسم مُدخل الأصل، وسجل التعديل يعرض اسم المعدّل بشكل منفصل. النسخ Duplicate هو إدخال جديد وينسب إلى من حفظ النسخة، دون نسخ اسم صاحب الأصل.
- تغيير اسم الحساب أو تعطيله لاحقًا لا يعيد كتابة أسماء الحركات السابقة.
- السجلات القديمة تعرض فقط الاسم/اسم الدخول الموثّق لديها؛ لا يُنسب سجل قديم للشخص الذي فتح الصفحة. إذا لم يوجد دليل لا يظهر اسم مختلق. القيود المولدة تلقائيًا تنسب إلى «النظام تلقائيًا».
- تسوية الراتب لها إسناد مستقل عن بند الراتب المولّد آليًا، بما فيها حسم السلفة غير النقدي.
- سجلات إدارة الحسابات لا تتضمن كلمات المرور أو بصماتها. API القائمة يُسقط الحقول السرية بانتقاء صريح.

## تجهيز الإصدار للمبرمج

هذا التعديل يضيف migration فقط: `20261101000000_users`. يحتوي جدول مستخدمين جديدًا وenum وفهرسًا وقواعد تحقق؛ لا يغيّر أي جدول أو مبلغ مالي قائم ولا ينشئ حسابات أشخاص تلقائيًا.

قبل تشغيل الإصدار على الخادم: خذ نسخة احتياطية قابلة للاستعادة، وطبّق migration عبر مسار النشر المعتاد (`npm run db:deploy`) ثم ولّد Prisma Client/ابنِ الصورة كالمعتاد. تحقق من صلاحيات دور التطبيق على الجدول الجديد باستخدام إعداد المنح الموجود. لا تستخدم reset أو migrate dev أو seed لمسح/إعادة تهيئة قاعدة الإنتاج. تحقق من دخول المالك أولًا ثم أنشئ الحسابات المطلوبة من التبويب.

لم تُعدّل ملفات Docker أو إعدادات أو مجلدات النشر أو بيانات الدخول الفعلية أو قاعدة المستخدم أثناء التطوير. حسابات الاختبار مؤقتة داخل ذاكرة قاعدة معزولة، وليست حسابات في نظام المستخدم.

## التحقق المنفّذ

- نجح 146 اختبارًا في 16 ملفًا، مع ESLint وTypeScript وبناء Next الإنتاجي.
- طُبّق migration على قاعدة PGlite فارغة ومعزولة للتحقق من SQL، واختُبرت APIs الحقيقية من بناء الإنتاج: إنشاء حسابات بواسطة المالك والمعدّل، رفض مشاهدة قائمة الحسابات أو أي POST مالي للمشاهد، تغيير الدور وكلمة المرور والتعطيل، منع الكتابة فوق version قديم، وحماية اسم المالك.
- تأكد فحص القاعدة أن محاولات المشاهد وإدارة الحسابات لا تغيّر قيود الصندوق الموجودة، وأن استجابات الحسابات وسجل تدقيقها لا يحتويان كلمات المرور أو البصمات.
- من المتصفح: حساب المعدّل أنشأ حساب مشاهدة وحركة دخل؛ ظهر «تم الإدخال بواسطة غيث» تحت الحساب والحركة. تعديل حركة بواسطة سامر أبقى اسم غيث على الإدخال وأظهر سامر في سجل التعديل.
- فُحصت واجهة المشاهد عبر الأقسام المالية العشرة، بما فيها صفوف مصروف ثابت وخدمة فعلية وهمية: لا أزرار كتابة أو إدارة مستخدمين، وسعر الصرف غير قابل للتحرير؛ تبقى أدوات البحث والتصدير متاحة.
- شُغّل اختبار الواجهة على منافذ loopback مع proxy اختبار يحقن هوية وهمية ثابتة وسياق Origin للقاعدة المؤقتة فقط، لا باستخدام كلمات مرور أو اتصالات الإنتاج. أُغلقت السيرفرات وقاعدة الذاكرة بعد الاختبار.
