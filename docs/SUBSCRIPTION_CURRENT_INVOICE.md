# تصحيح فاتورة الشهر عند تعديل الاشتراك — 2026-10-27

## السبب

كانت `subscription.update` تعدّل سجل تسعير الاشتراك فقط. مولّد الفواتير لا يعيد إنشاء فاتورة موجودة، بينما المتبقي في العميل مجموع فواتيره الفعلية ناقص الدفعات المخصصة لها. لذلك يظهر سعر الاشتراك 450$ وتبقى فاتورة الشهر بقيمة 600$.

## الاستخدام بعد نشر التعديل

1. افتح «الاشتراكات ← تعديل» للعميل.
2. أدخل القيمة الشهرية الصحيحة، مثل 450$.
3. اختر «فاتورة الشهر الحالي والفواتير القادمة» واكتب سبب تعديل الفاتورة، ثم احفظ.
4. إذا لم توجد أرصدة أقدم أو دفعات، تصبح فاتورة 600$ والمتبقي 450$. إذا كان مدفوعًا عليها 150$، يصبح المتبقي 300$.

يمكن حفظ نفس سعر الاشتراك 450$ إذا كان قد تغيّر سابقًا؛ تتم مطابقة فاتورة الشهر مع السعر دون تغيير السعر إلى رقم مؤقت. لا يشغّل نشر الكود تصحيحًا تلقائيًا لأي عميل: يلزم أن يحفظ المستخدم الاختيار المطلوب.

خيار «الفواتير القادمة فقط» لا يعدّل فاتورة الشهر الحالية. هذا أيضًا السلوك الافتراضي لأوامر API القديمة التي لا ترسل `invoiceScope`، حفاظًا على التوافق وعدم تغيير الفواتير دون اختيار صريح.

## الحماية والسلوك المحاسبي

- لا تعدّل الدالة سوى الفاتورة التي تطابق المنظمة والعميل والاشتراك وفترة الشهر الحالي ومعرّف الفاتورة الذي شاهدَه المستخدم. لا تمس فواتير الأشهر الأقدم أو `openingBalanceSnapshotUsd`.
- يحتفظ النظام بمعرّف الفاتورة ورقمها وتاريخ إصدارها واستحقاقها، ويعدّل بند الاشتراك الموجود دون حذف السطور أو الفاتورة. تبقى البنود الإضافية كما هي.
- تقبل إعادة التسعير فاتورة ذات بند اشتراك واحد بكمية 1، ومجاميع متسقة مع بنودها؛ ترفض الفواتير المخصصة غير المطابقة بدل تخمين طريقة تسعيرها.
- لا تحذف الدفعات أو تخصيصاتها ولا تنقل مبالغها السابقة بين الفواتير. يرفض التخفيض إذا صار الإجمالي أقل من المدفوع على الفاتورة. عند مساواة الإجمالي للمدفوع تصبح الفاتورة مسددة؛ عند زيادته يعاد فتح المتبقي.
- إذا زاد الإجمالي، يطبّق مسار FIFO أي رصيد عميل غير مستخدم أصلًا، دون إنشاء قبض جديد. إذا كان لنفس الدفعة تخصيص موجود على نفس الفاتورة، يزداد ذلك التخصيص بمقدار الرصيد غير المستخدم فقط مع حفظ معرفه وسجل `before/after`، بدل إنشاء تخصيص مكرر يخالف قيد `(paymentId, invoiceId)` الفريد. لا ينقص أو ينقل التخصيص القديم.
- يحمي `expectedInvoiceTotal` من نموذج قديم فوق تعديل متزامن، وتحمي المعاملة Serializable وidempotency الحالية عملية التسعير مع الدفع. إذا فشلت أي خطوة تتراجع المعاملة كلها.
- يسجل `AuditEvent` للفاتورة `before/after` للمبلغ والباقة والمتبقي والمدفوع والحالة، مع حساب المالك والسبب والتوقيت و`source: subscription-current-invoice-update`. يحفظ تحديث الاشتراك أيضًا قيم السعر والباقة والنطاق المختار.
- لا ينشأ `CashEntry` أو قيد عكسي؛ تعديل قيمة فاتورة غير حركة دخول أو خروج للصندوق.

## الملفات

- `lib/finance/contracts.ts`: خيارات نطاق تعديل الفاتورة ومعرّفها وإجماليها المتوقع وسبب التعديل.
- `lib/finance/service.ts`: تعديل فاتورة الشهر وحماية الدفعات والحالات وسجل المراجعة.
- `app/page.tsx`: اختيار النطاق وبيانات الفاتورة الحالية وسبب التعديل.
- `tests/subscription-invoice-update.test.ts`: حالات السعر القديم/الجديد والدفعات والفواتير المخصصة والنطاق والتزامن وإبقاء سجل الصندوق كما هو.

لا تغييرات schema أو migrations أو صلاحيات أو ملفات نشر، ولا اتصال بقاعدة المستخدم أثناء التطوير. اختيار المستخدم وإعادة حفظ الاشتراك بعد تثبيت النسخة هو ما يطبّق التصحيح على فاتورته الحالية.

## التحقق

- نجحت 115 حالة اختبار، وفحص TypeScript وESLint وبناء الإنتاج في نسخة فحص مؤقتة مطابقة لملفات التطبيق وملف القفل. استُخدمت مكتبات جديدة في النسخة المؤقتة لأن مكتبات الأصل ملفات سحابية غير محملة، دون تعديل حزم المشروع أو قفله.
- نجح اختبار API فعلي مع Next.js وPrisma وقاعدة PGlite مؤقتة (PostgreSQL عبر WASM) وmigration المشروع كاملًا. استخدم الاختبار دورًا محدودًا يملك SELECT/INSERT/UPDATE دون DELETE على الجداول.
- أُعيد إنتاج الحالة نفسها: سعر الاشتراك 450$ وفاتورته 600$، ثم إعادة حفظ 450$ بخيار الشهر الحالي جعلت الفاتورة والمتبقي 450$ مع نفس الرقم والمعرف ودون أي قيد صندوق.
- تحقق الاختبار من الدفعات الجزئية، رفض التخفيض دون المدفوع مع rollback، حالات PAID/PARTIALLY_PAID، الفواتير الأقدم والبنود الإضافية، رفض إجمالي قديم، idempotency، الرصيد الدائن غير المستخدم على تخصيص موجود، وبقاء النتيجة بعد إعادة القراءة. لم ينشأ أي قيد عكسي.
- تمت معاينة صف عميل وهمي باشتراك 450$ ومتَبقٍ 450$، ونموذج النطاق وسبب التعديل، وتبديل خيار الفواتير القادمة فقط في المتصفح. لم تستخدم المعاينة بيانات المستخدم.
- يبقى اختبار PostgreSQL تشغيلي متعدد الاتصالات على staging موصى به قبل النشر، خصوصًا تزامن تغيير السعر مع الدفع؛ جلسة WASM واحدة لا تثبت اختبار التزامن الحقيقي.
